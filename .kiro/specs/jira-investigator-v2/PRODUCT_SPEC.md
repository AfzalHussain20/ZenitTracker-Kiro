## 1. Vision

The Jira Investigator is an AI-assisted investigation platform built for QA leads, engineering managers, and developers. It analyses Jira data, discovers meaningful engineering patterns, and presents evidence-backed insights in an interactive report.

**It is not a chatbot that prints statistics.**

The investigation engine separates facts from findings from conclusions. Every finding references evidence. Every conclusion states its confidence level. The AI layer explains — it never invents.

---

## 2. Goals

### Primary Goals
- Surface engineering patterns that are difficult to see in raw Jira data
- Separate QA-owned metrics from developer-owned metrics
- Replace accusatory language with neutral, evidence-backed observations
- Make every conclusion explainable and reproducible

### Measurable Success Criteria
- A report renders in under 3 seconds after the investigation API call completes
- Every finding links to at least one supporting evidence item
- No AI-generated statistic appears without a reference to computed data
- Every chart is interactive (hover, expand, filter)
- Reports can be exported to PDF and shared via URL
- The system never uses the words "scam", "cheat", "abuse", or "inflation"
- Duplicate detection false positive rate is below 15% on known test data
- Every metric card has a tooltip: what it measures, why it matters, what it does not tell us

## 4. User Experience

### 4.1 Design Principles
- **Objective** — Describe patterns. Never accuse people. Never infer intent.
- **Layered** — Facts first, then findings, then conclusions. Always in that order.
- **Explainable** — Every finding has a "Why?" button showing the signals that produced it.
- **Transparent** — Every metric has a tooltip. AI-generated content is visually distinct from computed data.
- **Honest about uncertainty** — "Insufficient evidence" is a valid and explicitly shown outcome.

### 4.2 Visual Language

```
[Computed]  Green badge   Derived from Jira data. Deterministic. Reproducible.
[AI]        Purple badge  Narrative generated by AI from structured evidence.

[FACT]      Direct Jira data. No interpretation.
[FINDING]   Observation based on evidence.
[CONCLUSION] Hypothesis with stated confidence level.
```

### 4.3 Confidence Labels

All findings and conclusions display one of:

| Label | Meaning |
|---|---|
| `HIGH CONFIDENCE` | Multiple strong signals agree |
| `MEDIUM CONFIDENCE` | Several signals agree, some uncertainty |
| `LOW CONFIDENCE` | Weak or single signal |
| `INSUFFICIENT EVIDENCE` | Not enough data to conclude |
| `UNKNOWN` | Cannot determine from available data |

`UNKNOWN` is a valid outcome. The system never forces a weak conclusion.

## 5. User Flows

### 5.1 QA Lead — Reporter Investigation
```
1. QA Lead opens Jira Intelligence chat
2. Types: investigate reporter "Name"
3. Chat shows compact card:
   ✓ Reporter Investigation complete
   353 issues analysed  ·  Evidence generated
   [View Full Investigation →]
4. Clicks "View Full Investigation"
5. Report page opens at /investigations/{id}
6. Reviews Data Quality panel (what data was available)
7. Reviews Limitations section (what could not be analysed)
8. Reviews Facts section (raw counts — no interpretation)
9. Scrolls to Velocity Analysis
10. Sees a day flagged UNUSUAL (z-score 2.3)
11. Clicks "Why unusual?" → sees z-score explanation
12. Scrolls to Duplicate Investigation
13. Expands a LIKELY cluster → sees signal breakdown
14. Clicks ticket ID → opens Jira in new tab
15. Scrolls to Team Comparison → sees acceptance rate ranked
16. Reads AI Narrative section (labelled [AI])
17. Clicks Export → downloads PDF
```

### 5.2 Engineering Manager — Component Investigation
```
1. Manager types: investigate component "Video Player"
2. Investigation runs, report opens
3. Reviews root cause clusters
4. Sees cluster: 3 tickets, 3 platforms, 1 build
5. Expands cluster → sees all signals
6. Reads conclusion: ONE likely root defect (HIGH CONFIDENCE)
7. Shares URL with lead developer
```

### 5.3 Developer — Release Investigation
```
1. Developer types: investigate release "v8.0.63"
2. Report shows defects against this release
3. Sees component breakdown — Video Player highest
4. Sees root cause clusters grouped by component
5. Identifies 2 likely defects producing 9 tickets across platforms
6. Exports HTML for post-release review
```

### 6.1 Processing Layers

```
Layer 1  Raw Jira Data
         Issues, links, resolution, components, versions, description
         [Reused: fetchAll(), buildJQL() — unchanged]
              ↓
Layer 2  Analytics Engine
         Field extraction, counts, timelines, distributions
         [Reused: existing field mapping — add issuelinks/description/components]
              ↓

         Multi-signal duplicate detection, velocity z-score, cluster analysis
         [New: buildInvestigationReportV2()]
              ↓

         Facts → Findings → Conclusions, data quality report, limitations
         [New: replaces ASCII string output]
              ↓

              ↓
```

## 7. Investigation Engine

### 7.1 Facts Layer — Direct Jira data, no interpretation
```typescript
interface FactsLayer {
  totalIssues: number;
  dateRange: { from: string; to: string };
  statusCounts: Record<string, number>;
  priorityCounts: Record<string, number>;
  typeCounts: Record<string, number>;
  platformCounts: Record<string, number>;
  componentCounts: Record<string, number>;
  confirmedDuplicateCount: number;   // resolution="Duplicate" OR linked as duplicate
  resolutionCounts: Record<string, number>;
}
```

### 7.2 Findings Layer

#### Reporter Activity (reporter type — QA-owned only)
```typescript
interface ReporterActivity {
  bugsReported: number;
  activeDays: number;
  platformsTested: string[];
  componentsTested: string[];
  buildsTested: string[];
  severityDistribution: Record<string, number>;
}
```

#### Reporting Characteristics (NOT "Reporter Quality Score")
```typescript
interface ReportingCharacteristics {
  acceptanceRate: number;          // 1 - (invalid + byDesign) / total
  confirmedDuplicateRate: number;  // confirmed duplicates only / total
  invalidRate: number;             // "Not an Issue" / total
  reopenRate: number | null;       // null if changelog unavailable
}
```
> UI label: **"Reporting Characteristics"** — never "Score" or "Performance".
> Tooltip: "Describes patterns in filed issues. Reflects report characteristics, not individual performance. Many factors outside a reporter's control influence these numbers."

#### Velocity Analysis
```typescript
interface VelocityAnalysis {
  dailyCounts: {
    date: string;
    count: number;
    zScore: number;
    classification: 'UNUSUAL' | 'ELEVATED' | 'NORMAL' | 'LOW';
    teamCountThatDay: number | null;
    contextFactors: string[];   // ["sprint end day", "release detected", "team-wide spike"]
    explanation: string;
  }[];
  baseline: {
    mean: number; median: number; stdDev: number;
    windowDays: number; sampleSize: number;
    reliable: boolean;           // false if fewer than 20 data points
  };
}
```

Z-score thresholds:
- `UNUSUAL`: z ≥ 2.0
- `ELEVATED`: 1.0 ≤ z < 2.0
- `NORMAL`: −1.0 ≤ z < 1.0
- `LOW`: z < −1.0
- Fewer than 20 points → "Insufficient history — showing raw counts only"

#### Duplicate Analysis — Multi-signal confidence model

Signal weights:
| Signal | Weight | Availability |
|---|---|---|
| `resolutionIsDuplicate` | 0.40 | ✅ `resolution` field |
| `linkedAsDuplicate` | 0.35 | ✅ `issuelinks` field |
| `titleSimilarity` | 0.15 | ✅ existing |
| `descriptionSimilarity` | 0.15 | ⚠ needs `description` field |
| `sameComponent` | 0.15 | ⚠ needs `components` field |
| `samePlatform` | 0.10 | ✅ `customfield_10103` |
| `sameBuildVersion` | 0.10 | ⚠ needs `fixVersions` |
| `createdProximity7d` | 0.05 | ✅ `created` |
| `sameAssignee` | 0.05 | ✅ `assignee` |

Confidence gates:
- **CONFIRMED** (≥0.80): `resolutionIsDuplicate` OR `linkedAsDuplicate` fired
- **LIKELY** (≥0.55): ≥3 non-title signals each ≥0.5
- **POSSIBLE** (≥0.35): ≥2 non-title signals
- **INSUFFICIENT_EVIDENCE** (<0.35): not shown in main view

> **Hard rule:** Title similarity alone never produces CONFIRMED or LIKELY.

#### Root Cause Clustering
Groups issues likely manifesting from one engineering defect. Replaces "same-day cross-platform = suspicious" logic entirely.
```typescript
interface RootCauseCluster {
  clusterType: 'SAME_ROOT_CAUSE' | 'PLATFORM_SPECIFIC' | 'UNKNOWN';
  confidence: 'HIGH' | 'MEDIUM' | 'LOW' | 'INSUFFICIENT_EVIDENCE';
  tickets: string[];
  platforms: string[];
  components: string[];
  buildVersions: string[];
  interpretation: string;              // neutral language only
  alternativeExplanations: string[];
  engineeringDefectEstimate: number;
}
```

#### Data Quality Report
```typescript
interface DataQualityReport {
  fields: {
    name: string; available: boolean;
    coveragePercent: number;
    impact: 'CRITICAL' | 'HIGH' | 'MEDIUM' | 'LOW';
    affectedAnalysis: string[];
  }[];
  overallCompleteness: number;  // 0–100
  limitations: string[];        // auto-generated based on missing fields
}
```

### 7.3 Conclusions Layer
```typescript
interface Conclusion {
  id: string;
  confidence: 'HIGH' | 'MEDIUM' | 'LOW' | 'INSUFFICIENT_EVIDENCE' | 'UNKNOWN';
  statement: string;
  evidenceIds: string[];
  alternativeExplanations: string[];
  source: 'COMPUTED' | 'AI';
}
```

### 7.4 Dimension Scores (replace single investigation score)

Five independent scores. No aggregate. Each explains itself.

| Dimension | What it measures | Owner |
|---|---|---|
| `reportingActivity` | Testing breadth — platforms, features, active days | QA |
| `reportingCharacteristics` | Acceptance rate, duplicate rate, invalid rate | QA |
| `evidenceStrength` | % of findings with HIGH/LIKELY confidence | SYSTEM |
| `engineeringSignal` | Root cause cluster count and confidence | SYSTEM |
| `dataCompleteness` | % of critical fields available | SYSTEM |

Every score card has a tooltip: `whatItMeasures`, `whyItMatters`, `whatItDoesNotMeasure`, `howCalculated`, `knownLimitations`.

## 8. Report Design

### 8.1 Page Structure
```
/investigations/{id}

Header: ← Back | Investigation type | Date | Share | Export

Sidebar (sticky, desktop):
  Data Quality  ·  Limitations  ·  Facts
  [Type-specific sections]
  Evidence  ·  Team Comparison  ·  AI Findings  ·  Appendix

Main Content (sections rendered by investigationType)
```

### 8.2 Sections by Investigation Type

**All types include:**
1. Data Quality Panel — always first
2. Limitations — auto-generated
3. Facts — raw counts, [Computed] badge
4. Evidence cards
5. AI Findings — [AI] badge

**Reporter type adds:** Reporter Activity, Reporting Characteristics, Velocity, Duplicate Investigation, Platform Coverage, Team Comparison

**Release/Component type adds:** Defect Density, Root Cause Clusters, Platform Coverage

**Assignee type adds:** Developer Metrics only (fix time, reopen after fix, resolution SLA) — never mixed with reporter metrics

### 8.3 Evidence Card Design
```
[FINDING]  [LIKELY]  [Computed]

Title of the finding

Supporting Metrics:
  Metric A: value    Metric B: value    Metric C: value

Related Tickets: SUN-xxx  SUN-xxx  SUN-xxx  [↗ open in Jira]

[▼ Why was this detected?]

Alternative Explanations:
  • Could be explained by...
  • Insufficient data to rule out...

Engineering Impact: HIGH / MEDIUM / LOW / UNKNOWN
```

### 8.4 Explainability ("Why?" Button)
Every evidence card expands to show:
```
Why was this duplicate cluster detected?

  Signals evaluated for SUN-8788 ↔ SUN-8779:

  ✓ Resolution marked Duplicate    weight 0.40   value 1.0
  ✓ Same platform (Fire TV)        weight 0.10   value 1.0
  ✓ Created same day               weight 0.05   value 1.0
  ✓ Title similarity 91%           weight 0.15   value 0.91
  ✗ Linked as duplicate in Jira    weight 0.35   value 0.0
  ✗ Same component                 weight 0.15   value 0.0  [field unavailable]

  Combined confidence: 0.79  →  LIKELY

  Alternative explanations:
  • Could be the same bug discovered independently during regression testing
  • Component field missing — accuracy reduced

  Algorithm: duplicate-detector-v2.1  |  Detected: 2026-07-15T11:34:00Z
```

### 8.5 AI vs Computed — Visual Distinction
```
[Computed]  "Generated from Jira data using deterministic logic. Reproducible."
[AI]        "Generated by AI from structured evidence. Review independently."
```

AI sections include: *"The AI received pre-computed evidence items and was instructed not to generate statistics. All numbers reference computed facts above."*

### 8.6 Relationship Graph (Phase 2)
Visual interactive graph:
```
Reporter → Feature → Component → Platform → Developer → Resolution
```
Or cluster tree:
```
Video Player Crash (build 8.0.63)
├─ SUN-8788  LG TV
├─ SUN-8779  Fire TV
└─ SUN-8766  Android TV
```

## 9. AI Responsibilities

### AI does
- Write executive summary (references evidence IDs, not invented numbers)
- Generate recommendations (references specific findings)
- Explain complex findings in plain language
- Highlight trends found by the analytics engine

### AI must never
- Generate a number not in computed analytics
- Use: "scam", "cheat", "inflation", "abuse", "gaming"
- State intent: "X was trying to..." or "X deliberately..."
- Present a finding without referencing its evidence ID
- Use accusatory framing

### AI Prompt Structure
The AI receives:
1. Structured evidence JSON (not raw issues)
2. Computed facts
3. Explicit prohibition list
4. Data quality report (so it can reference limitations)
5. Instruction: "Reference evidence by ID. Use 'The data shows...' not 'X did...'"

## 11. Acceptance Criteria

### 11.1 Duplicate Investigation — Done when:
- [ ] Multi-signal detection implemented with weights as specified
- [ ] `resolutionIsDuplicate` and `linkedAsDuplicate` signals implemented
- [ ] Confidence label shown: CONFIRMED / LIKELY / POSSIBLE / INSUFFICIENT_EVIDENCE
- [ ] Title similarity alone never produces CONFIRMED or LIKELY
- [ ] "Why?" button shows full signal breakdown per pair
- [ ] Related ticket IDs are clickable links to Jira
- [ ] Alternative explanations shown for every cluster
- [ ] Algorithm version and timestamp stored in audit trail

### 11.2 Velocity Analysis — Done when:
- [ ] Statistical baseline computed: mean, median, stddev over 90 days
- [ ] Z-score shown per day
- [ ] Classification: UNUSUAL / ELEVATED / NORMAL / LOW
- [ ] Team average on spike days compared
- [ ] Context factors listed (release day, sprint boundary)
- [ ] "Insufficient history" shown if fewer than 20 data points
- [ ] Hardcoded thresholds (5/10) removed

### 11.3 Reporter Investigation — Done when:
- [ ] Only QA-owned metrics shown in reporter sections
- [ ] Resolution rate NOT shown as reporter performance metric
- [ ] Open issue count NOT attributed to reporter as their responsibility
- [ ] Acceptance rate shown with tooltip
- [ ] Confirmed duplicate rate (not title-similarity rate) shown
- [ ] Team comparison uses only QA-owned metrics
- [ ] Bug count ranking NOT shown as standalone performance comparison

### 11.4 Data Quality Panel — Done when:
- [ ] Every critical field shows availability and coverage %
- [ ] Auto-generated limitations based on missing fields
- [ ] Overall completeness score shown
- [ ] Panel appears before any findings in every report

### 11.5 Report Page — Done when:
- [ ] Facts / Findings / Conclusions labelled distinctly throughout
- [ ] [Computed] / [AI] badges on every section
- [ ] Every metric card has a tooltip
- [ ] Sticky sidebar navigation
- [ ] All charts interactive (hover, filter)
- [ ] Export to PDF works
- [ ] Shareable URL works
- [ ] Report loads from sessionStorage (no second fetch)
- [ ] Fallback to Firestore if sessionStorage empty

### 11.6 AI Narrative — Done when:
- [ ] AI receives structured evidence JSON, not raw issues
- [ ] Every AI sentence references at least one evidence ID
- [ ] No AI-generated number that isn't in computed facts
- [ ] Prohibited word list enforced in prompt
- [ ] [AI] badge on all AI-generated sections
- [ ] Disclaimer shown under AI sections
